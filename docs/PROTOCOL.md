# Протокол Du-HD4K

Описание соответствует реализации и результатам анализа в [первичном отчёте](2026-11-06_reverse-KYFPV-report.md). Подтверждён приём видео на Du-HD4K; управление полётом и полная совместимость с другими прошивками не подтверждены.

## Транспорт

| Назначение | Значение |
|---|---|
| IP дрона | 192.168.169.1 |
| Приём запросов дроном | UDP 8800 |
| Исходящий видеопорт дрона | UDP 1234 |
| Локальный порт клиента | Автоматически выделенный свободный порт |
| BL heartbeat | EF 00 04 00 |
| Интервал heartbeat в мосте | 110 мс |
| Период таймера WPF | 50 мс |
| Таймаут свежести ответа | 3 с |

UDP-сокет не вызывается с `Connect`, иначе ответы с порта 1234 будут отфильтрованы. Фильтр IP обязателен. BL допускает другой исходящий порт устройства; сохранённая ветка TX требует совпадения и порта.

## Полётная команда

`Protocol.Flight` формирует 8 байт:

| Offset | Поле |
|---|---|
| 0 | 66 — начало |
| 1 | Roll: крен, 1…255 |
| 2 | Pitch: тангаж, 1…255 |
| 3 | Throttle: газ, 0…255; входное 1 заменяется на 0 |
| 4 | Yaw: поворот, 1…255 |
| 5 | Флаги |
| 6 | XOR байтов 1…5 |
| 7 | 99 — конец |

Маркеры начала и конца, флаги и примеры пакетов записаны в hex. Смещения, размеры и диапазоны осей — десятичные. Нейтраль осей — десятичное 128 (80 hex).

| Флаг | Назначение в APK | В текущем интерфейсе |
|---|---|---|
| 01 | Взлёт | Да, импульс 1 с |
| 02 | Посадка | Да, импульс 1 с |
| 04 | Остановка | Да, импульс 1 с, газ 0 |
| 08 | Переворот | Нет |
| 10 | Безголовый режим | Нет |
| 20 | Unlock / fast return | Нет; семантика неоднозначна |
| 40 | Свет | Нет |
| 80 | Калибровка | Нет |

Примеры payload:

```text
Нейтраль: 66 80 80 80 80 00 00 99
Взлёт:    66 80 80 80 80 01 01 99
Стоп:     66 80 80 00 80 04 84 99
```

`FlightInput` вычисляет каждую ось как `128 + round(127 × clamp(speed, 10, 100) / 100 × axis)`, где axis находится в диапазоне −1…1. Правый стик задаёт roll/pitch, левый — yaw/throttle; четыре оси могут изменяться одновременно. Пары ограничены единичным кругом. Направления сохранены из прежнего клиента, физическая реакция дрона ещё не проверена.

## BL-оболочка команды

Все многобайтовые поля BL — little endian:

| Offset | Размер | Значение |
|---|---|---|
| 0 | 1 | EF |
| 1 | 1 | 04 |
| 2 | 2 | Полная длина: 12 + payload.Length |
| 4 | 4 | Sequence, увеличивается на каждую команду |
| 8 | 2 | Размер payload |
| 10 | 2 | Ноль |
| 12 | N | Payload |

Пример нейтрали при sequence=1:

```text
EF 04 14 00 01 00 00 00 08 00 00 00 66 80 80 80 80 00 00 99
```

При отключении после отправки полётных команд клиент также отправляет payload `65`, обнаруженный в Android-коде выключения контроллера. При простом просмотре видео он не отправляется.

Входящий BL-пакет начинается с `93`; offset 2 содержит его полную длину. Для входящего сообщения типа 3 длиной не менее 12 байт отправляется ACK `EF 08 08 00` плюс исходные байты 4…7.

## Видеофрагменты

Входящий пакет имеет тип `01` в байте 1:

| Offset | Размер | Поле |
|---|---|---|
| 8 | 8 | Frame ID |
| 32 | 4 | Индекс фрагмента, начиная с нуля |
| 36 | 4 | Число фрагментов |
| 40 | 4 | Размер scan-данных JPEG |
| 44 | 2 | Ширина |
| 46 | 2 | Высота |
| 48 | 1 | Качество JPEG |
| 56 | До 1024 | Данные фрагмента |

Неописанные байты не интерпретируются. Реализация повторяет формулу native-библиотеки: `count = size / 1024 + 1`, последний фрагмент имеет `size % 1024` байт. Не заменяйте её на округление вверх без отдельной проверки граничных размеров и прошивки.

Ограничения парсера: 1 МиБ данных кадра, до 1025 фрагментов, размеры 1…4096 по каждой оси. Метаданные фрагментов одного кадра должны совпадать. Поддерживаются перестановка и дублирование пакетов; неполный кадр не выводится.

Для качества 5/10/25/50/75/100 добавляется соответствующий embedded JPEG header размером 605 байт. На offsets 145/147 записываются высота/ширина **big endian**, затем scan-данные и маркер `FF D9`. При quality=0 данные с началом `FF D8` передаются как готовый JPEG.

## Подтверждения кадров

`BlFrames.Acknowledgement` создаётся для каждого 16-го фрагмента, последнего фрагмента либо полностью собранного кадра. Используется `EF 02`, длина uint16 и одна запись кадра. Offset 32 — frame ID, 40 — состояние (0 неполный / 1 полный), 44 — длина записи; с 48 идёт битовая карта полученных фрагментов, округлённая до uint32. Последние 8 байт оставлены нулевыми в соответствии с восстановленной раскладкой.

Это частичный перенос: не воспроизведены вся очередь четырёх кадров, запросы повторов и управление качеством оригинала. Успешное получение видео не означает гарантированную работу при больших потерях пакетов.

## TX и VLC

В исходниках оставлена ветка TX: heartbeat `01 01`, префикс `03` перед полётным payload, RTSP `rtsp://192.168.1.1:7070/webcam`. Она не используется текущим WPF-окном и не подходит подтверждённой BL-видеосессии пользователя.

Мост для VLC выдаёт `GET /video.mjpg` как `multipart/x-mixed-replace; boundary=frame`. Каждый раздел содержит `Content-Type: image/jpeg`, `Content-Length` и JPEG. Это HTTP MJPEG, не RTSP, без перекодирования.
